# Workshop Starter — общие проектные правила

Проект для локальной работы в Codex или Claude Code. Порядок действий — skill `workshop-copilot`; здесь — постоянные правила. Один пакет задаёт одинаковый workflow; доступные режимы и запросы разрешений зависят от среды.

## Работа

- Общайся по-русски; технические имена сохраняй на языке проекта.
- При старте проверь, что `AGENTS.md` лежит в корне открытой папки; если нет — назови папку, которую нужно открыть, и ничего не переноси сам. Кратко сообщи рабочую папку, видимые инструкции, применённый skill и известный режим разрешений; «неизвестно» — допустимый ответ.
- Режим выбирает пользователь в приложении: Claude Code — Auto, Codex — «Approve for me». Не ослабляй sandbox и запреты ради автоматизации и не переключай режим ради публикации.
- Пути относительны корню проекта; не подставляй пути автора пакета или конкретного пользователя.
- Согласуй до выполнения: новые существенные решения, установку программ, платные действия, изменение глобальных настроек, удаление или перезапись пользовательских данных, публикацию. Уже полученное подтверждение не спрашивай повторно.
- Чтение официальной документации и публичных данных (например, открытых API) в рамках согласованной задачи согласования не требует.
- Мелкая правка с понятным результатом (текст, цвет, отступ, опечатка, одна строка) — сразу, с проверкой и локальным commit, если Git уже есть; `docs/PRODUCT.md` и план не трогай, если требования не меняются.
- Меняй только нужные файлы, небольшими проверяемыми шагами. Не добавляй функции, зависимости и инфраструктуру без связи с задачей.
- Изменчивые технические сведения проверяй по официальным источникам.

## Стек по умолчанию

- Если пользователь не выбрал стек, начни с самого простого: файлы сайта (HTML/CSS/JS без сборки) — в папке `public/`; серверная часть — функции Vercel в корневой папке `api/`, только когда она нужна задаче. В корне проекта — `vercel.json` с `{"outputDirectory": "public"}`: без него Vercel публикует весь корень, включая правила и документы проекта (проверено живым деплоем).
- Зависимости и фреймворки — по согласованию. Нет Node, Python или Git — не устанавливай сам: предложи вариант без них или согласуй установку; отсутствие Git не блокирует работу.

## Проверка

- После изменения выполни релевантную проверку и покажи её фактический вывод. Различай «создано», «запущено» и «проверено».
- Статичные страницы проверяй у себя в браузере на ширине ноутбука и телефона. Серверные функции — на опубликованной версии Vercel, после согласованной публикации.
- Для расчётов сначала запиши контрольный пример в `docs/PRODUCT.md` и граничные значения; по возможности — тест до формулы.
- Ошибки разбирай по фактам — порядок в skill `debug-by-evidence`: воспроизвести, найти причину, проверить тем же сценарием, после двух неудачных попыток остановиться и доложить.

## Публикация

- Создание репозитория, push и deploy — только после «да» пользователя. Если «да» дано сразу вместе с запросом и в нём ясно, куда и с какой видимостью публиковать, второй раз не спрашивай: выполни и покажи в итоговом отчёте, что отправилось, кто видит код и сайт и как откатиться. Остановись и спроси, если нашёл проблему: секреты, не тот аккаунт, неожиданная видимость.
- Перед публикацией — ревью одним независимым reviewer в свежем контексте; порядок — в skill.
- В Codex правило проекта отправляет команды вида `git push …` на проверку, даже если раньше было сохранено «всегда разрешать»; в «Approve for me» её проводит автоматический reviewer — поэтому push выполняй только после явного «да» пользователя в этой переписке. В Claude Code `git push` дополнительно подтверждается пользователем по настройкам проекта.
- Если `git push` требует входа в GitHub, не проси токен в чат: предложи пользователю войти в своём терминале (`gh auth login --web --git-protocol https`, затем `gh auth setup-git`).
- После публикации проверь живую ссылку, основной сценарий и что служебные файлы недоступны: `<адрес>/AGENTS.md` и `<адрес>/docs/HANDOFF.md` отдают 404.

## Память

- `docs/PRODUCT.md` — цель, границы, критерии готовности, контрольный пример; `PLANS.md` — задачи; `docs/HANDOFF.md` — одно актуальное состояние, статус и следующий шаг в начале.
- Фразы «продолжаем проект», «где остановились», «подготовь handoff» запускают `workshop-copilot` без команды пользователя. Если штатный вызов skill недоступен, прочитай его `SKILL.md` и скажи об этом.
- После проверенного этапа кратко обновляй статус и следующий шаг; полный handoff — перед новым чатом или уходом. После автосжатия сначала сверь важные решения с файлами.

## Безопасность

- Для разработки используй тестовые данные. Не публикуй реальные ключи, credentials, session-файлы, логи с секретами или личные документы; не выводи их значения в чат и проверки.
- `.env.example` — только имена переменных и заглушки. Реальные значения — в локальном `.env` для backend либо в secret storage хостинга. Не помещай секреты в браузерный код, localStorage или публичные переменные сборки.
- `.gitignore` — фильтр для Git, не граница доступа. В Claude Code чтение секретов запрещено настройками проекта; в Codex такого запрета нет — не читай `.env` без необходимости. Перед commit/push проверяй состав и содержимое изменений.
- При найденном секрете останови публикацию и назови файл без значения; при утечке предложи сначала отозвать ключ.
- Не обходи разрешения среды; сообщай о конфликте, который мешает задаче.

## Развитие настроек

Starter — стартовая точка. Правила растут из реальных ошибок, а не заранее на все случаи.

- После завершённого этапа добавь к отчёту блок «Можно улучшить» — до трёх пунктов только по фактам этой работы: повторившаяся ошибка → правило или механизм; повторяемая процедура → skill; рутинная проверка, которую легко забыть → hook (в Claude Code нужен установленный интерпретатор, в Codex — одобрение через `/hooks`); идея по продукту. Нечего предложить — блок не пиши. Принятые идеи записывай в `PLANS.md` → Later с условием возврата.
- Ошибка повторилась — предложи одну строку правила и слой: этот проект (`AGENTS.md`) или личные настройки пользователя. Правило есть, а ошибка повторяется — предложи механизм: запрет или подтверждение в `.claude/settings.json` / `.codex/rules/`.
- Skill лежит в двух одинаковых копиях (`.claude/skills` и `.agents/skills`): правишь одну — правь обе.
- Правку настроек показывай конкретно и вноси после согласия; глобальные — только по отдельному «да».
